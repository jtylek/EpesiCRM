## Available now

- Browser: `/setup/migrate` (brand "epesi migration wizard", "Legacy Epesi data detected:", database name and the /data check) opens at once with the version read from the legacy files and a "Scan my epesi installation" button; the read-only scan starts only when it is pressed, a spinner ("Scanning your data...") shows while it runs, then the results replace the button; a failed scan shows a short message with a "Scan again" link. No setup code; 404 when the system is installed, in demo mode, or when no legacy installation is detected. The result is a short summary: legacy version, approval and blocking reasons, size, the installed modules that own data (found from the legacy `modules` table and the module's own install code, see `Detection/LegacyModuleData`: each recordset of `recordbrowser_table_properties` is listed under its module with its active record count, collapsing its ten tables; plain tables are summed (never listed by name); modules without data are not listed) with Core/Premium/Custom kind and whether each is migrated or kept untouched, and how many database tables belong to no listed module; never a per-table list; the full report is saved to `storage/app/migration-wizard/assessment.json`, and a link continues to the progress page. The migration makes no backup of its own and does not require the legacy maintenance mode: the administrator makes a full backup of the database and of the whole Epesi folder (Softaculous or another tool) and confirms it by typing `backed up` (`--confirm-backup`).
- CLI: `php artisan epesi:migrate-legacy --status` (also prints the recorded migration phase) and `--dry-run` (the same short summary; `--full` prints every table) are read-only; plain `php artisan epesi:migrate-legacy` rejects execution.
- CLI state machine (`--resume`, `Orchestration/MigrationRunner`): `--resume` continues from the last completed phase (`detected`/`assessed` -> `backed_up` (the typed backup confirmation, the only backup gate) -> `frozen` -> `tables_namespaced` -> `epesi_installed` -> `importing` -> `verified` -> `cleaned` -> `complete`), under `MigrationLock`; the exact table rename map is saved before the first table is renamed. There is no rollback: files are moved and tables dropped, so the only way back is the pre-upgrade backup. A failure is either a stop or an end. A stop (an interruption or a problem the administrator can fix: disk space, a timeout, a lost connection, another run holding the lock, a wrong administrator, a refusal before anything changed, a choice the operator still has to make) prints "Migration stopped. Fix the problem and run it again to continue." with the reason, and `--resume` continues. Anything else after the wizard began to change things (a failed install, an importer or data problem, verification blocked by a file or data problem) ends the run in the terminal `failed` phase: the reason is stored, `--resume` and every other state-changing step refuse and show "Migration failed and cannot continue. Reason: ... Please restore your Epesi directory and database from your backup, then switch PHP back to 7.4.", and `--status` still shows it. An unknown state refuses everything. The in-place import runs the app's own `import:legacy` importers against the renamed `legacy_<name>` tables (decision A in the plan note); verification input is built from the legacy tables, the imported rows, the file ledger and the coverage report. **Before the wizard changes anything** the operator must confirm a full backup of the database and of the full Epesi directory made BEFORE the upgrade (`--confirm-backup`, type "backed up" or `--yes`; never a default; read-only commands do not need it). Cleanup stays behind its own switch (`MIGRATION_WIZARD_CLEANUP=true` in `.env`, off by default) and needs only that backup confirmation and the release's own file list (`update/MANIFEST.txt`). Nothing has been run against a real installation. The typed confirmation moves the state to `backed_up`; `--resume` then freezes only with that confirmation, an approved schema and the matching database. A cleanup writes its list of removed files to `storage/app/migration-wizard/`. Old states that hold a `backup` or `restore_tested` key are tolerated and ignored.
- Browser: `/setup/migrate/progress` (`Filament/Pages/MigrationProgress`, no setup code, not in demo mode, 404 once complete or when no legacy installation is detected) shows the `--status` information and a Continue that runs the same `MigrationRunner` (same state, lock, ledger and gates; `Orchestration/PanelRun`, `RunnerFactory`) in bounded 20 second steps; the mail import keeps a checkpoint (`storage/app/migration-wizard/mail-checkpoint.json`) so a slice never re-walks all mails. Steps that cannot be cut (installing the tables, one record importer, verification, cleanup) run whole. Tested by Livewire and unit tests only; not yet opened in a real browser.
- Cleanup (`Cleanup/LegacyCleanup`, `LegacyFileClassifier`): it removes what is not Epesi 3, not hosting-owned and not preserved; there is no list of legacy files. Kept: every file the release lists (`update/MANIFEST.txt`), Epesi 3's runtime (`.env`, `app/`, `bootstrap/`, `config/`, `database/`, `lang/`, `public/`, `resources/`, `routes/`, `storage/`, `update/`), installed Epesi 3 modules, hosting-owned paths (`LegacyFileClassifier::HOSTING_KEEP`: `.well-known/`, `cgi-bin/`, `.user.ini`, `php.ini`, ...; reported), every `data/` area that was not migrated (`data/config.php` included: Epesi 3 does not read it and routes to the wizard only while no user exists), every file still in `data/CRM_Mail` / `data/Utils_FileStorage`, and every legacy `modules/` directory whose module no completed importer migrated (Premium and Custom among them). Removed: the directories of migrated legacy modules, the stock legacy root files and folders, and everything in `vendor/` the release does not list. Backup files (`.zip`, `.tar`, `.tar.gz`, `.tgz`, `.gz`, `.bz2`, `.7z`, `.rar`, `.sql`, `.sql.gz`, `.bak`) outside `data/` are left exactly where they are, listed as `backups_left_in_place` and not counted toward the archive cap; `data/logs` and `data/cache` are never archived. A path nobody listed is archived first (hashed archive, capped at 20,000 files / 200 MB; the refusal names the paths and says to move them outside the Epesi directory) and every removal is logged before the first deletion. A table is dropped only when its counts match (below) and no kept table still references it.
- Table certification: an importer declares the tables it brings over and any skip rule in one place (`CountedTables`). A table is released only when, counted in the database at verification time, source rows = records created from them + rows the declared rule skips (no tolerance) and no source id is missing. A mismatch keeps the table, reports both counts and blocks nothing. All side tables of a recordset (`_access*`, `_callback`, `_field`, `_edit_history`, `_edit_history_data`, `_favorite`, `_recent`) go with a certified `_data_1`, dropped with foreign key checks off on the cleanup connection only (restored in a `finally`); the five legacy `utils_watchdog_*` tables go as one exact group; a table no importer declares stays whatever its row count.
- Importer declarations: importers implement `CertifiableImporter` (legacy module, required/ignored columns, certified releases); `ImporterDeclarations` feeds them, with `LegacyModuleCatalog` (table ownership) and `ApprovedLegacySchemas` (version + per-module table shapes), to `ModuleCoverage`. Approval is per legacy module: the release must be 1.9.1 from both the database and the files, then each Core module is approved only when its own tables match the approved 1.9.1 shape; Premium, Custom and unknown tables never make the installation unapproved (they are preserved). An importer without a complete declaration stays unsupported; today `user_login`, `company_data_1` and `contact_data_1` are known-but-not-migrated and nothing is supported or certified.
- Administrator handoff: legacy password hashes are never imported. After the import, `--resume --admin-id=<legacy id>` sets a new password (hidden prompt, or the first line of stdin with `--admin-password-stdin`; never an option, never stored or logged) on the imported account of an active legacy administrator and makes it a super_admin (`Admin/AdministratorHandoff`). The state keeps only the legacy id.
- Operator choices: `--preserve=a,b` (exact legacy tables or file areas `data/<dir>`; `@unknown` keeps everything unclassified), `--discard=a,b` (exact names only, never a default, needs typing `discard` or `--yes`) and `--core-only` (keep known-but-not-migrated data) are stored in the state, validated, and shown by `--status` together with the backup confirmation and the completed importers. Premium and Custom module code and data are never removed unless an exact discard names their table or file area. Unknown data blocks cleanup until it is preserved or discarded by name. Files in `data/CRM_Mail` or `data/Utils_FileStorage` that no imported record references stay exactly where they are and do not block verification: they are listed (per area: count, bytes; the full path list in `storage/app/migration-wizard/leftover-files.txt`) and cleanup never removes them. A file an imported record needs but cannot be found, and any ledger problem, still block. `--status` and `--resume` print `left_behind`: per unmigrated module its code folder, `legacy_` tables and data folders, plus the unreferenced files and two notes (old SQL needs the `legacy_` prefix; `legacy_id` links migrated records to old rows). The `mail` and `attachments` importers run in place and MOVE their files (legacy mail attachments and notes' files) into the Epesi 3 file storage one at a time, each with a file-ledger entry made before the file is touched; rollback puts every file back. Preserved legacy Premium/Custom module code stays in its `modules/` directory untouched (it has no `module.json`, so it is never discovered or executed); it goes when that module is installed or updated. The wizard does not stop or wait for a web server.
- Legacy custom fields (extra columns): a Core recordset table with columns stock Epesi 1.9.1 does not have (`LegacyStockColumns`) is no longer a blocker. Every extra column of `company_data_1`, `contact_data_1`, `task_data_1`, `phonecall_data_1` and `crm_meeting_data_1` becomes a custom field of the Epesi 3 model, typed from its `<tab>_field` row (and display callbacks, e.g. `display_email` makes an Email field) or, for a column no row declares, from the SQL column type (`LegacyCustomFieldPlanner`, the mapping of `AI-shared/recordbrowser/fields.md`). The importer creates the definitions before the rows (idempotent by model and name), fills the values and replays them into History; links to other records (a company's Account Manager) are filled once those records exist. The page lists them ("Fields that will be added during migration"). A module is blocked only by a missing required column (`id`, `created_on`), by more than 64 extra fields on one model, or by an extra column on a table that cannot carry it (the message names the columns). A field added without its data (a file field: the ledger does not carry it yet; a link to a recordset Epesi 3 does not have) keeps the legacy table: verification does not release a table with an `unmigrated_columns` entry.
- "Can be migrated" is driven by the registered in-place importers (`InPlaceLegacyImport::LEGACY_MODULES`), not by the shape fingerprints: a module is listed when its importers exist, the release is 1.9.1 and nothing blocks it. Utils_Watchdog, Base_Dashboard, Base_Acl and the other system modules (Base, Base_Admin, Base_HomePage, Base_Notify, Base_Setup, Base_User_Settings, CRM_Calendar, Premium_ExchangeRate, Premium_Import, Premium_PrintTemplates, Tools_WhoIsOnline, Utils_BBCode, Utils_Messenger, Utils_RecordBrowser) are not listed (`AssessmentSummary::HIDDEN_MODULES`).
- Obsolete legacy tables: `recordbrowser_search_index` and the old Roundcube engine's own tables (`rc_cache`, `rc_cache_index`, `rc_cache_messages`, `rc_cache_shared`, `rc_cache_thread`, `rc_session`, `rc_searches`, `rc_system`, `rc_dictionary`, `rc_users`, `rc_identities`, `rc_contacts`, `rc_contactgroups`, `rc_contactgroupmembers`) are exact, user-approved names, never a pattern (`rc_accounts_*`, `rc_mails_*` and the other Epesi record tables are never included). They need no `--discard`, never block verification, and are dropped as soon as verification has passed, whatever the cleanup switch says; `--status` reports `obsolete_tables` and `obsolete_tables_dropped`. There is no rollback: the pre-upgrade backup holds these tables, and restoring it is the way back. An explicit `--preserve` keeps a table. No other table is dropped without an explicit approval.
- Size advisory: CLI is recommended when the assessed database is **at least 100 MB (100,000,000 bytes)** or **100,000 estimated rows**, when scanned files reach **1 GiB** or **10,000 files**, or when file enumeration cannot complete. Database row counts are metadata estimates. An advisory does not certify that browser execution is safe.
- No legacy maintenance mode is required: once Epesi 3 is unpacked over the old folder the old site no longer runs, so nobody can write legacy data. The wizard still rejects changed legacy configuration or schema fingerprints.
- Deterministic importer dependency planning, fingerprint-bound monotonic checkpoint validation, and read-only keyset batch reading (maximum 1,000 records per batch) are implemented as building blocks. Core users, companies and contacts now declare importer contracts and produce a read-only dry-run plan; row conversion and verification are not implemented. **No importer is certified, so verification can only end in `core_complete_with_preserved_data`; no legacy table is dropped.**

## Safe administrator assessment

1. Do not expose backup archives through the web server.
2. Confirm the CLI runtime: `php -v` (this checkout requires PHP 8.3+).
3. From the EPESI 3 application root run `php artisan epesi:migrate-legacy --status`.
4. Run `php artisan epesi:migrate-legacy --dry-run` and review its schema fingerprint, coverage and execution advice.
5. Make a full backup of the database and of the whole Epesi folder yourself (Softaculous or another tool), outside the application tree; the wizard makes none.
6. Confirm it by typing `backed up` on the progress page (or `--confirm-backup`); nothing is changed before that.

**Do not run production migration:** the CLI execution engine, importer mappings, persistent resumable checkpoints, target isolation, and end-to-end recovery verification are unfinished.

## Design constraints

The eventual CLI and browser execution paths must share one safety-gated engine. Unknown/custom/Premium tables and attachments must be preserved. Never evaluate legacy PHP configuration, automatically download legacy SourceForge distributions, or assume archive checksums prove recoverability.

See `AI-shared/migration/overview.md` for current decisions and
`AI-shared/migration/design/` for the original architecture and acceptance gates.
